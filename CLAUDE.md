# Правила работы с кодом

## Общие принципы

Всегда сначала опирайся на уже существующую архитектуру, стиль кода, названия и структуру проекта. Не создавай решения в вакууме, если в кодовой базе уже есть подходящие сервисы, интерфейсы, базовые классы, конфиги или точки расширения.

Не пиши функции и классы, которые живут отдельно от архитектуры проекта. Любая новая логика должна встраиваться в существующие слои и использовать текущие механизмы, а не создавать параллельную систему.

Код должен быть читаемым без комментариев. Если нужен комментарий чтобы объяснить что делает строка — это сигнал что нужно переименовать или разбить на части.

## SOLID

### S — Single Responsibility
Один класс или компонент — одна ответственность. Не смешивай UI, логику, хранение данных, ввод и сцену в одном месте.

### O — Open/Closed
Код должен расширяться без переписывания старого. Новое поведение добавляй через новые классы, стратегии, интерфейсы или наследование там, где это уместно.

### L — Liskov Substitution
Наследники должны полностью заменять базовый тип без поломки ожидаемого поведения.

### I — Interface Segregation
Предпочитай маленькие, узкие интерфейсы вместо одного большого. Классы не должны реализовывать лишние методы.

### D — Dependency Inversion
Зависеть нужно от абстракций, а не от конкретных реализаций. Используй DI и интерфейсы, а не жёсткие связи.

## Unity-правила

- Используй Zenject для внедрения зависимостей.
- Используй UniTask вместо корутин в новом коде.
- Храни конфигурационные и статические данные в ScriptableObject.
- Предпочитай чистый C# для логики. MonoBehaviour используй только там, где он нужен для сцены, Unity lifecycle или связи с Unity-компонентами.
- Стремись к слабой связанности через интерфейсы, абстракции, virtual/override, события и композицию.
- Пиши код так, чтобы его было легко расширять, тестировать и переиспользовать.
- Не используй `GetComponent` в Update или других hot-path методах. Кешируй ссылки в Awake или через инжекцию.
- Не используй `Find`, `FindObjectOfType` и подобные методы поиска по сцене — они медленные и создают неявные зависимости.

## Магические числа и строки

Никаких магических чисел и строк в коде. Любое число или строка которая что-то означает — выносится в именованную константу, поле ScriptableObject или enum.

Плохо:
```csharp
if (health < 20) { ... }
animator.Play("idle");
yield return new WaitForSeconds(0.3f);
```

Хорошо:
```csharp
if (health < _config.CriticalHealthThreshold) { ... }
animator.Play(AnimationNames.Idle);
await UniTask.Delay(_config.TransitionDelay);
```

## Поля и SerializeField

Все поля которые нужны в Inspector — помечай `[SerializeField]`. Никогда не присваивай значения приватным полям прямо в коде если они должны настраиваться снаружи или зависят от контекста проекта.

Плохо:
```csharp
private float _speed = 5f;
private int _maxHealth = 100;
```

Хорошо:
```csharp
[SerializeField] private float _speed;
[SerializeField] private int _maxHealth;
```

Или ещё лучше — вынести в ScriptableObject:
```csharp
[SerializeField] private PlayerConfig _config;
```

Значения по умолчанию допустимы только для технических вещей которые не меняются в зависимости от контекста (например индекс массива начинается с 0).

## Static

Не используй `static` поля, свойства и методы кроме случаев:
- Константы (`static readonly` или `const`) без состояния
- Хэши для Animator (`static readonly int`)
- Чистые утилитарные методы без состояния и зависимостей

Никакого `static` состояния, синглтонов через `static Instance` и глобальных менеджеров. Для доступа к сервисам используй Zenject.

Плохо:
```csharp
public static GameManager Instance;
public static int Score;
private static float _timer = 5f;
```

Хорошо:
```csharp
// Только так — без состояния
private static readonly int SpeedHash = Animator.StringToHash("Speed");
public const int MaxPlayers = 4;
```

## Именование

- Приватные поля: `_camelCase`
- Публичные свойства: `PascalCase`
- Интерфейсы: `IПascalCase`
- Методы: `PascalCase`
- Локальные переменные: `camelCase`
- Константы: `PascalCase` или `UPPER_CASE` — единообразно в проекте

## Приоритет

Сначала соответствие текущей архитектуре проекта. Потом переиспользование. Потом расширяемость. Потом локальная простота. Не ломай существующую систему ради краткости.
